## 仍需调整，按优先级排序

### P1：包变更与 Host 生命周期统一协调

`server/backend/restart.py` 的安全点只等待设备作业；权威随后向 Host 发 `mode=immediate, scope=process`。包下载、依赖安装、源码切换和台账写入没有进入这个闸门。隔离探针在包写锁被持有、设备作业为空时确认 `_watch` 仍进入重启执行分支；执行分支被替换为记录调用，没有真实重启。

下一步应在 Host 侧先关闭新包写入和受管设备启动入口，等待在途包变更结束，再允许退出；取消重启时只释放重启自身持有的闸门。backend 通过现有控制面获取或请求这个状态，不新建进程所有者。测试至少覆盖安装中重启、超时保持运行、取消后恢复，以及刚检查空闲就收到新安装的竞争窗口。

`device_processes.py::_package_dirs` 目前按台账直接组装源码路径；包升级/卸载期间启动新的 slave 也需要与这个闸门协调。`enabled` 当前主要决定主 Host 的启动扫描，显式指定包的 slave 并不据此禁用；这个语义应在前端说明清楚。

### P1：包操作持久化与崩溃恢复

当前 operation/log 仅在内存中，写锁仅在当前 Host 内有效。源码异常回滚已补齐，但在旧目录移入备份后被强杀，仍没有持久意图记录来自动恢复。依赖安装写入共享解释器，也没有随源码回滚。

需要明确“可恢复的源码/台账事务”与“不可自动回滚的共享依赖安装”两种状态：操作 ID、阶段、旧/新路径先落盘；启动发现未完成操作时进入恢复或明确阻断，不能自动重放安装或设备动作。是否引入独立包环境应另行评估，不在这轮悄然改动 dev 的环境机制。

### P1：正式前端接上 dev 合同

正式 `uni-lab-fe` 已能构建和预览，但这不代表 dev API 已兼容。本轮检查仍能看到 FE 要求 `workflow_type`、发送 `inventory_bindings`，并使用 Task/Job 的 `topological_index` 等字段。已有逐项差异见 [V1/dev 消解清单 F01–F09](v1_dev_reconciliation.md)。源码中没有检出直接使用新 driver-packages 和 scheduler/drain 路径，包管理/runtime 的正式页面或 adapter 仍需接入。

先完成 dev 的工作流列表 → 预检 → 创建任务 → 状态读取最小闭环，再对接物料、驱动包和生命周期管理。非空库存绑定、修订和优先级不能通过丢弃字段伪装兼容。Center 的路由继续由 Center 持有。

### P2：旧 Workspace 中确需保留的业务逐项归位

管理入口换为 runtime，不代表 V1 的所有 Workspace 业务都已迁移。物料源布局预览/版本冲突、模板校验等按需要归入现有 Graph/Materials 和 Registry；旧发布同步不恢复为另一套权威。旧 `/v1/snapshot`、通用 operation/revision/eventCursor 协议目前也没有兼容层；若无现存调用方则无需重建。

此前列出的工作流返回值 if/else、parallel 作者语法、预计时长、资源区间和执行开始许可，仍属于独立业务待补项，继续在 dev 工作流/调度层实现。完整范围见 [Workspace 盘点](workspace_host_cleanup.md) 和 [V1/dev 消解清单](v1_dev_reconciliation.md)。

建议接下来的实现顺序：先关闭包变更与 Host 重启/新 slave 启动的竞争窗口，再补包操作恢复，随后接正式前端最小运行链路。
