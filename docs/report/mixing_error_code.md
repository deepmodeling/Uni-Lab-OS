# Mixing 设备 UniLab 报错码说明

## 1. 文档范围

本文档以当前代码实现为准，说明 Mixing 设备报警如何从 PLC 软元件地址转换成 UniLab 报错码，以及 PLC 报警不可用时如何回退到 Action 运行失败分类。

相关代码：

- 报错码及 PLC 地址映射：`unilabos/devices/workstation/szlab_poly_studio/error_codes.py`
- PLC 报警读取接口：`unilabos/devices/workstation/szlab_poly_studio/plc.py`
- Task 运行失败上报：`scripts/task_execution_coordinator.py`

## 2. 报错码分层

当前实现包含两类报错码。

### 2.1 PLC 明确报码：`101` 起

这类报错码直接对应《报错信息.csv》中已经写明含义的 PLC 报警位，例如：

```text
D518.5 = ON
    ↓
MIX-S09-106：天平无法连接
```

PLC 报警是当前的优先结果，因为它来自明确的硬件或 PLC 状态，而不是根据文字猜测。

### 2.2 Action 回退报码：`001` 起

当 Action 返回 `success: false` 或抛出异常，但没有读到已置位的 PLC 报警时，UniLab 根据设备 ID 和失败信息进行回退分类。

例如：

```text
等待 S06 准备信号失败
    ↓
MIX-S06-001：泵加液工站未就绪或未动作
```

`001` 类报码表示 UniLab 已确认动作失败及所属工站，但不一定已经确认具体的物理故障位。

## 3. 运行时处理顺序

Task Action 结束后，处理顺序如下：

1. Action 正常成功：记录成功结果，不生成报警。
2. Action 返回 `success: false`：提取返回值中的 `message` 或 `error`。
3. Action 抛出异常：使用异常文本作为原始失败信息。
4. 根据设备 ID 确定所属工站。
5. 读取该工站和公共区域已映射的 PLC 报警位。
6. 如果存在置位报警，使用对应的 `101` 类精确报码。
7. 如果没有置位报警或报警节点不可读，使用 `001` 类 Action 回退报码。
8. 将结构化错误提交给 Task API，Task 进入失败处理流程。

当公共报警和工站报警同时置位时，当前映射顺序会优先返回公共报警，例如急停或通信异常。

## 4. PLC 报警读取方式

对每个报警位，代码按以下顺序尝试读取：

1. 读取符号位变量，例如 `S09报警[0].NO[5]`。
2. 如果符号位不可读，读取对应 BOOL 数组，例如 `S09报警[0].NO`，再取指定 bit。
3. 如果数组也不可读，读取原始 D 字，例如 `D518`，再通过位运算判断第 5 位。

只有值为 `ON`、`True` 或相应 bit 为 `1` 时才会上报。CSV 中没有注释的预留位没有加入映射。

PLC 设备提供 Action：

```text
get_active_mixing_alarms
```

返回示例：

```json
{
  "success": true,
  "alarm_count": 1,
  "has_alarm": true,
  "alarms": [
    {
      "code": "MIX-S05-101",
      "error_code": "MIX-S05-101",
      "station": "S05",
      "title": "拍照伺服报警",
      "plc_address": "D510.0",
      "plc_variable": "S05报警[0].NO[0]",
      "recovery": "暂停 Task，切换手动模式，排除报警原因后复位；确认工站准备好再恢复自动运行。"

}
```

没有报警时返回 `alarm_count: 0`、`has_alarm: false` 和空数组。

## 9. 当前限制

1. 只有 CSV 中带明确注释的位被映射；预留位不会报警。
2. PLC 报警节点必须通过 OPC UA 暴露。可以使用符号位、BOOL 数组或 D 字中的任一种读取方式。
3. Task 协调器目前在 Action 失败后读取报警位；它不是持续后台扫描器。
4. `get_active_mixing_alarms` 可用于主动查询，但当前不会自行暂停 Task。
5. 如果 PLC 报警位尚未置位、已经过早复位或 OPC UA 节点不可读，系统会使用 Action 回退报码。
6. 当前只选择读取结果中的第一个活动报警作为本次 Action 的主错误；主动查询接口会返回全部活动报警。
7. S04 和 S06 在 CSV 中没有带注释的专用工站报警位。S04 已增加六位置传感器初始化前检查；S06 主要使用 Action 回退报码。公共报警仍然适用。
8. S10、S11 已有 PLC 精确报码，但当前 Action 回退目录没有为它们定义 `001` 类报码。

## 11. 与《Mixing 设备操作与故障处理指南》的逐项对照

本节中的“实现”专指当前代码是否能够在运行时自动形成 UniLab 报警，不表示现场故障已经具备自动恢复能力。

状态定义：

- **已实现**：代码有明确检测条件，条件出现后可自动生成对应报码。
- **部分实现**：已经有报码，但依赖 Action 返回失败或特定文本；缺少指南所描述物理原因的直接传感器判定。
- **未自动实现**：即使定义了报码，当前运行链路也没有能够触发它的检测规则。

### 11.3 尚未实现的具体检测能力

以下现象目前不能仅靠现有代码可靠确认：

1. S05 拍照电脑是否关机或锁屏、拍照程序是否运行、照明灯是否真实点亮。
2. S05 旋转机构的实际角度是否正确。
3. S06 Task 是否把泵加液 Action 设置为跳过。
4. S07 注粉过程中重量是否持续不变、粉罐是否空罐、注粉机构是否失控持续运行。
5. S08 瓶体或瓶盖的实际位置以及机构是否发生物理干涉。
6. S09 TIP 是否缺失、重复、歪斜、折断或实际触底。
7. S12 实际轨迹、实际目标位置与动作编号是否符合 workflow 预期。
8. S12 报警时夹爪当前是否仍持有物料；只有 `D524.2` 能确认“产品掉落”，不能代表所有持料状态。

## 13. 调试前端显示与完整结构化结果存储

### 13.1 前端显示

Mixing Action 运行失败后，调试前端会在“工艺变量与过程日志”中额外显示一条红色错误明细，格式为：

```text
报错码：MIX-S09-106 · 工站：S09 · PLC 地址：D518.5 · 错误：天平无法连接 · 处理建议：检查天平电源、通信线和通信参数，恢复连接后重试
```

显示字段直接来自后端返回的结构化错误对象：

| 前端字段 | JSON 字段 |
|---|---|
| 报错码 | `error_code` |
| 工站 | `station` |
| PLC 地址 | `plc_address` |
| 错误说明 | `message` |
| 处理建议 | `recovery` |

前端优先读取 Action 日志的 `detail.reported_failure`；没有该字段时读取 `detail.result`。PLC 报警会在 Action 日志落库前完成映射，因此前端获得的是包含精确 PLC 地址和处理建议的最终结构。

### 13.2 完整结构化结果保存位置

| 用途 | 保存位置 | 完整结果路径 | 持久性 |
|---|---|---|---|
| 当前调试页面实时日志 | `TaskActionLogStore` 进程内缓存 | 日志条目的 `detail.result` 或 `detail.reported_failure` | 不持久化；调试后端进程重启后清空 |
| 运行历史数据库 | `%USERPROFILE%\\Documents\\UniLab_test\\run-history\\history.db` | SQLite 表 `action_events` 的 `detail_json`，其中为 `result` 或 `reported_failure` | 持久化 |
| Task 编排工作区 | 与 workflow 同目录的 `<workflow文件名>.task-workspace.json` | `task_instances[].execution_state.records[].error`；暂停时也写入 `pause_reason.detail.error` | 持久化 |

运行历史目录可通过环境变量 `UNILABOS_RUN_HISTORY_DIR` 修改。按当前用户和默认配置，数据库完整路径是：

```text
C:\Users\Fish\Documents\UniLab_test\run-history\history.db
```

当前仓库内一个 Task 工作区文件示例是：

```text
task-orchestration/szlab_robot_action_workflow.json.task-workspace.json
```

其中，`action_events.detail_json` 是调试运行中最可靠的完整日志快照；`action_records.error_json` 还会保存异常类型、异常消息和 traceback，但它主要是异常包装信息，不应替代上述结构化结果。

### 13.3 PLC 报警中止与等待超时

设备动作等待 PLC 完成信号时，不再先无限等待 Action 返回后才检查报警。公共等待链路现在同时处理三种结果：

1. 目标变量或传感器条件满足：动作继续执行。
2. 任一已映射 Mixing PLC 报警位变为 ON：立即中止当前等待，Action 返回失败，并优先使用触发中止的精确 PLC 报码、地址和处理建议。
3. 没有报警但超过等待时间：Action 返回该工站的超时或一般失败报码。

默认等待超时为 300 秒，可通过 PLC 设备参数 `mixing_wait_timeout` 修改，也可通过环境变量 `UNILABOS_MIXING_WAIT_TIMEOUT` 全局覆盖。报警轮询默认间隔为 0.5 秒。

该机制覆盖使用公共 PLC 等待函数的 S04、S05、S06、S07、S08、S09 和 S12 动作；S05 拍照结果、S07 注粉过程、S08 工艺完成以及机械臂内部的夹爪、参数写入和 S071 空位等待等原独立循环也已增加报警中止和超时。

全部 29 个报警映射都会同时核对单个位节点、父报警字、根报警数组和 D 寄存器；该规则统一适用于公共报警以及 S05、S07、S08、S09、S10、S11、S12。例如 `D518.2` 会依次核对 `S09报警[0].NO[2]`、`S09报警[0]`、`S09报警` 和 `D518`。这是为了兼容部分 OPC UA 服务中单个位节点存在但数值不刷新的情况；即使位节点错误地保持 `False`，父报警字的第 2 位为 ON 仍会触发 `MIX-S09-103`。

例如 S09 取 TIP 时，如果 `D518.2` 变为 ON，无需等待 `S09工艺完成 == 5`，当前等待会立即结束并上报：

```text
报错码：MIX-S09-103
PLC 地址：D518.2
错误：移液枪错误
处理建议：暂停 Task，切换手动模式并复位，检查 TIP 后初始化移液枪动作模块。
```
