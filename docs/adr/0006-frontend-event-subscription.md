# 前端事件订阅与有限重连窗口

状态：已采用。

`frontend_event` 保存 REST 状态的失效通知。新页面通过 REST 获取当前状态，
不需要播放所有历史通知。此前无游标的 SSE 从零读取，每页 100 条之后固定
等待一秒，导致约 1.3 万条历史把实时变更延后两分钟，并触发无效 REST 重读。

## 订阅与续传

- `/api/v1/events` 缺少或空白 `Last-Event-ID` 时，先转发尚未投影的定义通知，
  再在发送 HTTP 响应头之前固定最新持久序号。只订阅该序号之后的通知。
- 首次连接发送无 `data` 的 `id` 水位帧，供浏览器在尚无新业务通知时断线续传。
- 显式 `Last-Event-ID: 0` 表示回放当前保留的历史；其他合法游标排他续传。
- 每页仍限制为 100 条；`has_more` 为真时让出事件循环后立即读取下一页，
  追平后每秒检查。空页继续发送保活注释。保留原有非法游标错误合同。
- 前端在每次 `open` 和 `stream.reset` 后重读 REST。建连前已经发出的请求
  必须先等待结束，再启动新读取；单纯复用旧请求无法覆盖快照与订阅的时间窗。
- 同时只进行一轮刷新；突发通知合并，刷新期间到达的新通知保留一次后续刷新。
  运行通知也刷新活动任务详情，不能只更新任务列表缓存。

## 保留、过期与数据库重置

HTTP 应用生命周期管理一个后台任务，即使没有订阅者也清理通知。默认目标为
最近 24 小时、最多 10,000 条，每 60 秒启动检查，每事务最多删除 1,000 条；
积压清理在有界事务之间让出执行机会。以下 `BasicConfig` 字段均为正整数，
支持配置文件及对应的 `UNILABOS_BASICCONFIG_...` 环境变量：

| 字段 | 默认值 |
| --- | ---: |
| `frontend_event_retention_seconds` | 86400 |
| `frontend_event_max_count` | 10000 |
| `frontend_event_cleanup_interval_seconds` | 60 |
| `frontend_event_cleanup_batch_size` | 1000 |

延迟初始化时，HTTP 装配层向后台任务注入就绪等待。等待只发生在后台任务中，
不阻塞 HTTP 启动；运行时在服务原子发布后，通过线程安全通知立即唤醒首次
清理。状态检查与等待者登记共用发布锁，兼容提前发布并避免错过通知。初始化
失败或功能禁用时结束等待，由原启动路径报告故障；服务就绪后的真实清理失败
仍输出 ERROR 并重试。应用关闭会取消等待或等待当前清理事务完成，再退出任务。
清理模块不依赖 Web 占位代理或它的异常类型。

数量和时间是定期清理目标，不是每次插入后的硬限制。清理只删除连续序号前缀；
若转发通知的发生时间乱序，按时间清理在首条仍需保留的通知处停止，避免窗口
内部缺口；数量上限仍能约束增长。始终保留最新一条通知作为持久水位，即使
该条已经超龄，避免空闲库的水位回退。不修改运行日志、任务或审计表。

事件页与最早/最新保留序号使用同一条 SQL 的快照读取。每页都检测游标，
包括清理正在越过的慢连接。过期游标收到 `stream.reset`，`data.reason` 为
`cursor_expired`；大于最新序号的游标收到 `cursor_ahead`（例如数据库重置）。
该帧的 `id` 是新的最新水位，随后保持连接，继续发送新事件。客户端必须重读
REST，不能把 reset 当成某个特定任务的业务变更；Python 客户端同样处理水位回退。
工站控制通知的 REST 读取接口增加 `reset_required`，过期时返回新的 `next_cursor`。

选择 SSE 内的命名控制事件而不是 HTTP 410：浏览器原生 EventSource 对非 200
响应会失败，业务代码也无法直接从 error 回调读取响应体。重读状态后恢复订阅
与 Kubernetes watch 的过期恢复原则相同，传输方式适配原生 EventSource。

数据库原地替换后若恰好重用了同一序号范围，单一整数游标无法识别库代际；
每次重连补读 REST 提供状态收敛。本协议是状态失效通知，不承诺逐条审计投递。
