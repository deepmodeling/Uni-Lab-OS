# 设计理念与系统边界

Uni-Lab-OS 希望把设备能力、实验步骤和物料状态组织成可执行、可观察、可追溯的实验系统。
实验人员不必关心某个动作通过哪一种通信后端执行；驱动作者也不应同时实现调度器、前端和数据库。
本章解释这些边界为何存在，以及它们在本版中的实际含义。

版本固定为 [手册入口](index.md) 的 dev 提交。这里的设计目标不等于所有故障恢复、硬件或规模场景都已验收。
字段和调用方式分别见 [API 全目录](api-catalog.md) 与对应业务章节。

## 1. 一份能力声明，多种接入方式

设备驱动首先是一段实现设备能力的 Python 代码。`@device`、`@action`、类型注解、默认值和说明文字
共同描述它能做什么、需要什么参数、会返回什么结果。注册表把声明变成供界面、工作流、调度器和工具读取的合同。
设备包可以同时携带驱动、物料模板、设备图和示例工作流，独立于主仓库维护。

这让人工与 AI 编写的代码使用相同入口，但不意味着“代码能够 import”就表示设备可以投入实验。
注册表发现、设备初始化、在线能力上报、动作执行和结果验证是不同阶段。前端既要查静态声明，
也要查 endpoint 的实际路由；不能将已安装的类显示为已连接的硬件。

业务驱动尽量不依赖传输层。通用执行与物料操作由 `backend.runtime` 承担，HostLink 与 ROS2
各自完成节点初始化、通信和执行适配。Workstation 动态子设备也必须初始化对应 backend 的 node，
而不只是保存一个 Python 对象。具体声明与导入路径见 [驱动接入](python-cli-mcp.md)。

HostLink 适用于普通 Python 驱动、服务调用、状态通知及跨设备物料处理；ROS2 保留原生生态的能力。
**HostLink 不支持 MoveIt、RViz，也不是任意 ROS API 的等价实现。** 高频图像等 ROS 原生需求继续选择 ROS2，
并按设备的 `supported_backends` 声明和实测结果选型。

## 2. 决定何时执行，与实际执行分开

微后端负责判断任务是否可以执行：依赖是否满足、资源是否可用、库存是否足够，以及异常之后如何处理。
Host/Slave 负责执行已经下发的动作并报告事实。即使这些组件运行在同一台电脑上，职责也不合并。

| 组件 | 它负责的事 | 不应偷偷代做的事 |
| --- | --- | --- |
| 微前端 / 调用 API 的应用 | 参数编辑、绑定确认、提交任务、展示状态、提交人工决策 | 自己判定物料权威、伪造执行成功、直接改数据库 |
| 微后端权威 | 工作流定义与快照、任务、调度准入、锁、库存预留、物料与注册表、决策推进 | 将“命令发出”当作“设备已经完成” |
| Host | 执行路由、HostLink、受管进程、执行记录、遥测及日志汇报 | 发生错误后绕过调度自行重做实验动作 |
| Slave / 设备 node | 驱动调用、本地物料投影、服务与状态发布 | 用本地树覆盖服务端事实，替其他设备分配工作 |
| 上游平台 | 通过约定接口接入数据与控制能力 | 仅凭后端名称，假定已实现任意双向同步和冲突合并 |

默认启动时，管理进程持有统一 HTTP 端口，并看护 Host 子进程。Host 不监听第二个 HTTP 端口；
Host 专属请求由管理进程通过控制通道中继，在 Host 内部处理后回传结果。Slave 连接 HostLink 端口，
不是浏览器使用的管理端口。这样 Host 重启时管理界面可以继续工作，也可以明确告诉用户“执行端暂不可用”。

独立权威、远端 Host 和单进程调试有不同装配，见 [启动模式](python-cli-mcp.md)。
当前控制服务仍只有一个活动 Host 控制连接；不能由上述职责划分推导出“任意多个独立 Host 已可同时接入一个控制槽”。
一个 Host 管理多个 Slave，与这个限制并不矛盾。

## 3. 先确定事实的归属，再设计同步

同一件物料只有一份权威身份。名称用于展示与有范围的查找，UUID 用于引用；重名、设备重启和树移动
不能悄悄把它变成另一件物料。PLR 实例是本地操作对象，不因 Python 构造成功就自动成为权威物料。

推荐流程是：构造草稿，提交物料权威，获取服务器登记后的树，再用返回的实例操作和挂载。
不要继续使用旧草稿，或自行在 Edge/Cloud 之间维护两套身份映射。启动图的 adopt 登记是独立入口，
会以已登记物料为准；不能把启动图当作每次重启都强制恢复的物料备份。

| 概念 | 表达什么 | 不等于什么 |
| --- | --- | --- |
| template / template_name | 物料的可复用定义与业务模板标识 | 当前实例身份、PLR 实现类 |
| material | 一件已登记的设备或物料及其生命周期 | 所有内容物和位置都塞进同一行 |
| position / Site | 空间位置、父子关系、可挂载位点 | 普通拓扑连线、库存数量 |
| material data / substances | 物料业务数据、液体等内容物及量纲 | 调度资源锁、库存账务 |
| lot / reservation | 按批次记录的可用量与任务预留 | 一个容器里面的实时液面或液体组成 |
| category | 分类与前端兼容提示 | 后端按类别强制准入的白名单 |

位置和内容数据分开，是为了让频繁换位不搬运整份复杂内容，也让 liquids 等不同内容有自己的模型。
category 尽量保持为相应数据模型的字段，而非为每个分类再建一套关联层。
不强制 category 兼容，并不表示不校验 UUID、所属范围、版本或位点占用；这些仍然是数据正确性的边界。

PLR 反序列化只读取 `config.type` 来确定实现类，不回退到外层 `type`、`klass` 或模板名。
部分模型仍保留历史字段，不能把“禁止兜底解析”误写成“所有旧字段已经删除”。详细对象与单位见 [物料合同](materials.md)。

### transfer 是业务操作，不是两次本地树编辑

跨设备转运由 `materials` 门面进入权威：提交归属/位置变化，通知来源设备卸载，再通知目标设备加载权威树。
ROS2 和 HostLink 都应遵守这条链路，目标设备加载走自己的服务，不能由前端把序列化树同时塞进两台设备。

权威数据库事务不能包住两台设备的内存操作。网络中断时可能出现“权威已更新，设备投影尚未同步”；
HTTP 503 也不能证明数据库没有写入。处理方应核对账本、权威树和两端投影，并按幂等规则补同步，
不能换一个命令身份盲目再转运一次。创建、挂载、卸载、移位与内容变更的区别见 [物料操作](materials.md)。

## 4. 四个数据库按写入特征分工

拆库的主要目的，是隔离遥测和历史等高频/大体量写入，减少它们对调度及物料业务读写的影响。
它不是为每个模块增加一套“自己的事实”，也不表示四个库之间天然存在跨库原子事务。

| 数据库 | 主要内容 | 为什么单独存 |
| --- | --- | --- |
| runtime.db | 工作流、任务、执行控制、endpoint、注册表、运行配置等 | 调度与管理需要及时读取和推进 |
| materials.db | 模板、实例、位置/Site、内容数据、lot、预留与变更账本 | 物料一致性、身份和数量约束集中处理 |
| telemetry.db | 设备遥测事件、来源顺序、最新状态 | 高频上报不挤占任务与物料事务 |
| history.db | 执行/决策/反馈事件与不可变 payload | 长期审计与大正文独立增长 |

因此“设备当前状态”主要查 telemetry 的 latest state；“这次动作运行到哪里”查 task/job；
“设备是否在线、有哪些动作”查 endpoint。三个答案来自不同生命周期，不能以一个 busy 字段互相替代。

跨进程以 API 和协议 DTO 交互，不让浏览器或驱动直接读写任意 SQL 表。数据库连接与 SQL 管理属于实现细节，
身份校验、版本推进、幂等、账本与通知属于业务操作。文件目录叫 service 或 repository 并不能替代这个边界。
实体自身的版本、命令身份和来源游标用于协调跨库/跨进程变更，不能拿一个库的 sequence 当作全系统事务号。

每个库声明 `schema_version` 和一串线性迁移，库内版本记在 `PRAGMA user_version`。库内版本较低且迁移连续时，
启动会先备份为 `<file>.pre-v<N>-<时间戳>.bak`，再在一个事务里执行迁移，并与当前声明逐表核对结构，不符就整体回滚。
改表必须提升 `schema_version` 并补迁移（`tests/server/test_database_schema_versions.py` 固定各库指纹）。
改 CHECK / 列约束用 `rebuild_table_migration`（建新表 → 拷贝同名列 → 删旧表 → 改名 → 重建索引，依赖视图与触发器原样重建），
迁移里的建表语句是该版本冻结的字面量；`runtime.db` 的迁移链在 `tables/runtime/migrations.py`。
没有迁移路径时，开发期四个库都改名保留为 `.bak-时间戳` 后重建空库；正式发布前 `runtime.db` 与 `materials.db`
改为拒绝启动并保留旧库原样（`on_unmigratable="refuse"`），届时 `BasicConfig.database_rebuild_on_mismatch = True`
可显式允许重建。
升级前仍建议备份，不应带着正在执行的实验直接试升级。
实现依据：[数据库初始化策略](https://github.com/deepmodeling/Uni-Lab-OS/blob/862ce87a38222ac2d51739f2f89e5daecd3cd907/unilabos/server/database/schema.py)。

## 5. 提醒“哪里变了”，再读取“变成什么”

实时通道承载变更通知，HTTP 读取完整内容。这样大物料树、日志正文和任务快照不必被每次广播重复发送，
慢页面也可以按照自己的读取进度恢复。控制连接和观察连接必须分开，否则新打开的浏览器可能替换执行端会话。

| 链路 | 当前方式 | 观察者的处理 |
| --- | --- | --- |
| 权威与 Host 控制面 | runtime.v1 WS + HTTP 命令/结果正文 | 只由执行 Host 接入；不是前端订阅口 |
| 前端工作流/日志提醒 | `/api/v1/events` SSE | 收到相关变更后按身份拉取；日志用各自游标 |
| 前端物料提醒 | `/api/v1/materials/events` SSE | 根据账本进度刷新物料/树，重连时补读 |
| Host 与 Slave | HostLink TCP RPC/通知 | 按设备路由、服务和物料合同处理 |

每个浏览器自己持有游标；关闭一个页面不应使另一个页面丢掉读取进度。日志轮转、截断、断线后可能需要重新取快照。
并非所有通知都有可重放的持久事件 ID，例如日志轻通知不是审计账本。不能仅靠“没收到消息”判断设备没发生变化。

这是设计方向，不是“WS 中绝无正文”的承诺：当前 `backend_http` 中继仍会携带编码后的请求体。
同样，SSE 服务内部可能读取数据库检查变化；它与每个前端每秒全量 GET 不同。字段、重连与背压限制见 [实时协议](realtime.md)。

## 6. 模板是预设，确认后才成为运行输入

工作流模板表达实验语义，具体图绑定实验室里的设备与物料；一次 task 保存该次运行的快照。
子工作流帮助复用步骤，但最终设备动作仍由调度器下发，不是把一个任意 Python 脚本当作可恢复工作流。

模板中的 `T1` 可以预填，让用户理解要选择哪个位点，但它既不是 UUID，也不是用户已经确认的选择。
浏览器保存草稿用 preserve，显式确认资源与 Site；API 导入可用 resolve，在目标范围内解析唯一 Site。
无匹配或多匹配必须报错，不能自动选第一项。只替换声明为 SiteSlot 的参数，不能改写任意同名字符串。

提交界面应区分自动、逐步和单点。逐步模式每次放行一个物理尝试，切回自动仍继续同一 task；
一次按钮的网络重发复用幂等键，多页面更新使用 control_revision 检查。任务控制命令是 step / resume / pause / cancel
（pause = 转逐步并停止派发新动作；cancel = 停止派发并请求取消在跑动作，锁保持到设备真实返回）。
具体流程见 [运行与 Site](workflows.md)。

前端 card 的“待补充数量”应包含缺失参数和未确认绑定。服务端当前没有专门替前端返回这个数字的 API，
所以这是微前端接入规范，不是已经由后端生成的字段。

## 7. 重试是一段新历史，不是抹掉失败

一张工作流定义可以产生多个 task；一个 task 的逻辑节点有 node-run；同一 node-run 发生重试时，
产生新的 job，并用 attempt_group_uuid、retry_of_job_uuid 等字段关联。观察界面既应看得见逻辑进度，
也应能展开每次物理尝试及决策。

动作发生错误后，执行端打开 error gate，等待后端取得决策并通知放行。
非人工替换路径上报 failed，后端消费终态后决定重试、跳过或中止；重试仍受调度准入与逐步许可约束。
**当前实现不是先创建 retry job 再上报原 job 的 failed，也不是 Host 内部 while 重试。**

人工干预可以提供替换结果，但要留下原始错误、确认人和替换链。软超时的 wait 表示动作仍在执行并继续等待，
不是启动第二个动作；硬超时/取消也不保证 Python 线程或物理设备已经停止。对真实硬件的急停能力必须独立验证，
不能以界面显示超时替代硬件安全机制。

状态告警、动作错误和工作流人工确认是三种入口。普通状态 recommendation 不自动执行恢复动作；
涉及阻塞联锁时按 incident 的实际状态推进。错误选项、上限、超时与记录方式见 [异常与干预](workflows.md)。

## 8. 锁声明集中使用，不升级为隐式嵌套锁

物料天然带锁：动作的物料入参（`ResourceSlot`、`List[ResourceSlot]`、`Optional[ResourceSlot]`，或
`placeholder_keys` 标为 `unilabos_resources` 的入参）默认在执行期间独占。只读、不改变物料的入参用
`@action(materials_free=["参数名"])` 排除；`@action(materials_need_lock=[...])` 显式给出最终集合，
`[]` 表示整个动作不锁物料，两者不能同时写。注册表条目里的 `materials_need_lock` 是推导后的最终列表，
运行时先解析实际 UUID，再交调度处理；可选物料入参未传或为空时没有物料，也就不加锁。
YAML 注册表条目同一规则：不写 `materials_need_lock` 即默认，`placeholder_keys` 标为 `unilabos_resources`
的字段加锁（`materials_free` 排除）；`--complete_registry` / `--check_mode` 只把显式声明写回 YAML，默认值每次加载重新推导。
物料资源锁保护同一对象的并发使用；库存 reservation 保护某批次的可用数量；Site 占用表达物料所在位置。
三者不是同一个标志，也不能互相代用。

本版没有兑现父组预占、子组继承、组内并行再次竞争的完整层次锁。驱动内部确有硬件同步需求时，
本地锁可以保护临界区，但不能把大量未向调度声明的等待隐藏在一个“always_free”动作里，
再宣称系统获得了全局最优排程或跨进程死锁处理能力。

## 9. 可恢复不等于无条件重放物理动作

网络重发、消息补投递与实验重试必须分开。幂等请求复用同一身份；实验重试有新的 job；
执行结果不确定时先对账，不能以重启或超时为理由自动再做一次吸液、投料或机械臂移动。

本版已有持久任务/执行记录和部分 inbox/outbox，但控制面的部分缓存仍在内存。
不能承诺整个系统在任意断电点都 exactly-once，或持久化字段存在就代表恢复流程已经穷尽验证。
同理，普通 HTTP API 当前没有统一认证层，公开部署必须额外落实访问控制和 TLS。
Legacy 连接旧后端是显式边界，本次不修改它，也不为新协议增加隐式兼容回退。

## 10. 文档与发布的完成标准

接口文档要同时说明字段、调用者、状态变化、失败后怎么办，而不仅列出一份 OpenAPI。
本手册因此分为设计、路由全目录、物料/工作流/实时等业务章节及迁移说明。
自动导出的 JSON、参考表和校验脚本只留本地，不进入可发布的 developer guide。

七个 demo 分别覆盖组网、Workstation、异常、复杂工作流、物料、锁与库存，
配套测试进一步核对真实模板中的参数、Site、attempt 和数量变化。
它们是回归入口，不是所有设备已经获得生产认证；声明的 ROS2/HostLink、单进程/分离部署和 Jazzy/Humble 矩阵
也必须分别有测试证据。验收清单见 [七个 demo](../readme_demo_tests.md) 和 [迁移边界](migration.md)。

与历史《设备接入与贡献规范、OS 配合模式》的逐项差异见 [旧规范对照](reference-comparison.md)。
