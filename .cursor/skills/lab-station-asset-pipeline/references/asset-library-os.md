# 标准资产库、实例图与 OS 领域包

读取时机：资产入库、耗材拆分后交付、重复摆放、资产行为封装、从多个资产搭建 OS 项目。目标是让消费方只需资产、项目声明和已安装依赖，即可创建自己的工站，不需要发布者的源仓或原始 CAD 工作目录。

## 1. 先定位实际合同

读取当前资产库索引、一份最新有效原生包及现有封装/校验工具；路径从环境配置取得。核对实际使用的 OS 模块路径、版本、领域包 manifest、装饰器、graph 和 Sites 合同。工程所在仓维护设备规则，资产管线维护转换与封装，OS 维护调度/库存。

本技能的拆分、身份和职责规则适用于新项目；下面的文件树是当前 UniLab 原生库约定。已存在明确版本的 schema 时按它生成，不另创平行的 asset.json、库存账本或插件注册协议。需要实现 OS 声明/工作流时，若环境有 `unilab-domain-repo-builder` 技能，按它核对实际 OS 合同；没有时直接检查已安装 OS 与可运行领域包，不依赖作者的技能路径。

## 2. 标准资产库

入库必须同时执行 [公共字段、分类与正式入库](catalog-intake.md)：统一条目是 13 字段业务权威，分类字典/来源映射与工程包索引分工维护。

既有物理分区包括 `01_零部件`、`02_工件与耗材`、`03_机构模块`、`04_设备`、`05_工站与布局模板`；历史实现还可能有工程知识目录。它们不是完整业务分类树，沿用实际封包器和索引中的路径，不把旧知识目录自动等同 `tool`。统一业务类型采用六种 `resource_type`，旧包的 `reuse_kind` 仅作兼容转换。沿用库中 manufacturer ID 与安全 slug；内部设计可用 `unilab`。同一定义维持 asset ID，内容变更追加修订。

### 资产命名：一律中文

入库定义使用**中文名**，允许字母（例如 `SPR检测模块`、`Dianthus检测模块`；产品名本身含字母或型号时保留）。同一中文名同时用作：

- 包目录名 `<分类>/<厂家>/<中文名>__<修订>`
- 目录条目 `original_name` 与 USD 入口文件名（`<中文名>__r001.usdc`）
- `title` 用于展示，可带型号与图纸号

约束与例外：

- USD prim 标识符受 `SdfPath` 限制只能用 ASCII，**不把中文写进 prim 名**；原始中文名写入 `lab:sourceName`，由中文名派生的 prim 名做 ASCII 化处理。
- 入库生成的 `slug()` 使用 `\w`（含 CJK）并只折叠其他符号，中文不会被转写掉；如果目标库实现会把中文剥掉，先修工具或记录例外，**不要静默退化成英文名**。
- 内部脚本、图节点 id、分组键可以保留 ASCII；交付名以库内中文名为准，二者映射写进入库清单。
- 已经以英文名发布的资产改名时保留原 `asset_id`，以新中文路径发布新修订，旧路径留作历史，不新建平行身份。

标准目录示例：

```text
Asset_library/
├─ library.json                 # 工程包、固定修订及旧前端兼容索引
├─ 统一目录/
│  ├─ library.json             # 从条目重建的业务检索索引
│  ├─ 条目/<uuid>.json         # 13 个公共字段，model.targets 关联工程包
│  ├─ tags.json                # 历史标签档案；规范分类索引位置从配置读取
│  └─ sources.jsonl            # 原始字段与来源证据
├─ 02_工件与耗材/unilab/vial_small__r001/
│  ├─ com.nvidia.simready.packaging.json
│  ├─ .metadata/
│  │  ├─ com.nvidia.simready.packaging.bom.json
│  │  └─ com.nvidia.simready.root_usds.json
│  └─ simready_usd/
│     ├─ vial_small__r001.usdc
│     ├─ unilab.json
│     └─ readiness.json
└─ 03_机构模块/unilab/capper__r001/
   ├─ com.nvidia.simready.packaging.json
   ├─ .metadata/...
   └─ simready_usd/
      ├─ capper__r001.usdc
      ├─ unilab.json
      ├─ readiness.json
      ├─ cad/...                 # 有交付需要时保留
      └─ behavior/...            # 有资产专属行为时保留
```

使用现有原生封装器计算 manifest、文件 BOM 与摘要，更新库索引；不手写伪摘要。CAD、纹理、USD 依赖、运动数据和源码都必须进入声明的闭包。USD 几何入口与 Python 入口分开：例如 `behavior/usd.py` 不能覆盖模型 `usd` entrypoint。验证源路径、包内相对路径和入口内容，迁出原目录再重开。

### 入库前查重（强制门）

封装前先检索现有库，命中就不要再入库：

1. **身份检索**：按 manufacturer + model + slug + 规格/配置查 `library.json` 的 records/packages；同一料号命中时直接比对 `definition_revision`，不要新建 `__rNNN` 目录。
2. **语义检索**：型号不同但用途/规格相近时（如同一"5000 mL 广口瓶"或"1000 µL 导电 tip"），核对规格、配置、几何与安装/接口 frame；只有这些合同一致才算同一定义。
3. **几何指纹**：对候选资产与本次源模型计算（网格数、三角形数、按 1 mm 取整的世界包围盒、逐网格三角形数集合）。完全一致 → 复用；仅包围盒/规模接近 → 逐项核对，按"疑似重复"记录，不自动合并。
4. **结论落盘**：入库清单里每项写明 `reused_from`（被复用 asset_id + 依据）或 `dedup_scan`（检索到的候选与判定理由）。命中项从 `ingest` 输入中删除，改为在布局/领域包中直接引用其 asset_id。
5. **例外**：只有确认无匹配、或匹配项缺本工站必需的表示/接口/修订时，才生成新包；同一资产的内容变更走追加修订，不新建 ID。真实差异（如左右镜像件、不同行程模组）按不同定义保留，并写明差异字段。

查重失败而重复入库会造成同物多定义，后续布局、碰撞与库存无法共用身份，属于验收不通过项。

本技能已携带通用转换、入库、原生校验与物化实现，入口及依赖见 [portable-tools.md](portable-tools.md)。目标库使用其他明确版本 schema 时核对兼容性；发布索引/服务器操作沿用实际库工具与授权，候选包未满足目标 schema 前标为待入库。

正式库保存定义与固定修订；场景摆放、物料 UUID、占用、运行数据库和任务输出保存在项目中。耗材拆分与实例数量规则见 [identity-assembly.md](identity-assembly.md#耗材与重复摆放)。完整工站可以作为布局模板引用这些定义，不能用一个整站 USD 或一个装满瓶子的合并 mesh 替代可单独操作的耗材资产。

先在 staging 生成候选、验证摘要和 USD 闭包。已授权发布时沿用库的修订机制，读回后更新同一目录记录的目标，保留旧锁可解析。补充 CAD、行为或其他表示不创建第二个资产 ID／目录条目；内部修订目录不当成新资产展示。用户明确要求原路径更新时遵从该要求，并处理受影响的摘要和固定引用，不擅自建立平行资产。仅修改技能或讨论设计不触发服务器发布。NVIDIA 命名的封装格式和写入物理字段均不授予物理/任务资格。

CAD 文件与引用式装配的保存、SolidWorks 配合和冷消费验收，见 [CAD 与装配标准](cad-assembly.md)。

## 3. 定义、实例、库位与状态的归属

### 零部件 → 机构模块 → 设备

资产类别及停止拆分位置以 [decomposition-boundaries.md](decomposition-boundaries.md) 为准。`04_设备` 同时容纳保持整机的商业成品和由机构引用组装的自动化设备；前者不要求拆成机构。`01_零部件` 保存完整采购件或静态支撑；`03_机构模块` 保存独立运动/夹持单元及行为。例如完整光电传感器为一个部件，三份使用三个实例；光纤头与放大器是否合并为完整组件由用户决定。可分开安装的组件在同一资产中声明安装 frame，在实例上覆盖安装位姿，不能为每份安装复制一套定义。

机构的运动轴、限位、输入/输出安装 frame 保存在自身元数据中；行为使用注入的运动端口。设备保存固定资产依赖、机构角色、安装层次和协调脚本，调用机构方法。机构无需各自变成顶层 OS 设备；设备是对 OS 的 Action 边界，内部机构可作显式逻辑别名。只在确有独立调度需求时注册额外设备。

组合 USD 保留引用与可动父子关系，固定内容摘要；原生包要求完整闭包时携带依赖 USD 的校验副本，并记录其来源包摘要。项目消费时校验副本与对应资产相同。资产定义、装配实例、运行时可动状态分开。若 OS graph 中的内部节点只是别名，明确真实模型 prim 与位姿权威，不能同时叠加两套模型或将别名的零坐标当成安装位姿。

完整传感器几何与感知模型分别验收。用户指定底部朝上的光电检测时，只为这些实例绑定射线，不把轴限位传感器自动改成射线。发射原点、方向、量程与依据随资产保存；运行时由真实引擎创建传感器并读回命中/距离。CAD 光束示意属于 guide，不作为实体碰撞体。几何射线命中不证明透明/反射率响应、实物标定或物料身份。验证复制后的独立位姿、无遮挡/遮挡/退出、相邻通道、父级移动和真实读取；未执行的后端标为未验收。

| 内容 | 保存位置 | 关键约束 |
|---|---|---|
| 几何、尺寸、安装/TCP/抓取 frame、可用孔位 | 资产 USD 与 unilab.json 的 parameters / interfaces_data | 资产局部坐标；frame 有单位及来源 |
| 资产专属设备行为、轴协调、动作前提 | 资产 behavior/*.py 与 behavior_binding | 与资产版本共同封包 |
| 重复数量、设备实例、父子层次、装配变换、模型绑定 | 项目 OS graph；沿用已有布局文件 | 多实例共享定义，各有稳定 instance ID |
| 实例的端口、工具、后端、标定和角色映射 | 项目配置 / bindings | 按实际类型区分配置、几何和观察结果 |
| 库位类型和允许物料 | 资产接口数据，生成 OS resource / Sites 声明 | 同一架定义可生成多套独立 Site 实例 |
| 当前物料 UUID、父级、占用、开盖状态/内容状态 | OS 运行时库存、Site 与物料/试剂结算 | 可由盖的归属推导开盖状态；避免另一套独立权威 |
| 调度、Claim、重复回报处理、原子结算 | 现有 OS | 设备返回结果/见证，OS 决定结算 |

资产槽位如 A1 是定义标签，不是所有项目共享的 Site UUID。瓶身和可拆盖各有独立身份；盖离开瓶后挂到夹持头/库位，复盖返回该瓶的 cap Site。规划和视觉可维护观察状态，但不能把命令目标或仿真过程账本直接当成 OS 已结算库存。

### 库位几何与尺寸验收

新增或修改有物理位置的库位时，必须量取并记录其有效边界与适用尺寸，不能以“已有 frame／允许耗材类型”代替几何定义。每个库位都要有测量结果或明确缺项；同构阵列可复用有证据的尺寸定义，但要核对各实例的变换及边角、异形位等例外。纯逻辑库位标为不适用，不虚构体积。

分开保存以下语义，复用包内现有 `parameters / interfaces_data` 及其实际 schema，不另建平行库位权威：

| 内容 | 资产必须交付的信息 |
|---|---|
| 放置基准 | 所属 link／prim、局部 frame、支撑面轮廓与法向、放置朝向；说明原点是底面中心、角点还是其他安装基准 |
| 可容纳空间 | 在库位局部坐标下量取内边界、有效深度／净空及障碍范围；区分真实腔体、开放承载区和按已知限制定义的允许包络 |
| 允许物料 | 类型及有依据的外形、姿态、插入或突出条件；耗材标称尺寸、载架外包围盒与槽内可用尺寸分别记录 |
| 显示表示 | 明确是支撑面、腔体还是近似包围体；保存形状、尺寸、相对放置基准的中心偏移与朝向，近似项标出适用范围 |

优先从原 CAD 的实际支撑面、内壁和限位特征测量，并对照厂家图纸或实测。每项尺寸绑定来源摘要、组件／特征或图纸定位、单位、测量方法、容差／不确定性与确认状态；照片标定按 [source-routes.md](source-routes.md)。换了槽型、适配器或 CAD 配置后复核受影响边界。

矩形库位明确局部 X/Y/Z 对应的长宽高、全尺寸还是半尺寸、边界相对基准的位置；按消费者实际字段约定转换。圆孔记录孔径和有效深度，异形位记录轮廓或可解析的边界几何。显示用的长方体只是声明过的近似，不能自动当作可放置空间或碰撞体。旋转库位先在本地轴系量尺寸，再施加实例变换；世界轴对齐包围盒不能回填为局部长宽高。

高度无依据时保留未知，交付已有的支撑面轮廓和“净空未确认”；未知不编码为零高度或任意默认高度。开放托盘也要区分已知无上盖与整站上方净空尚未检查。资料不足的库位可随候选/视觉资产交付，但尺寸与适配资格保持待确认。

验收覆盖本次声明的全部库位，逐项保存来源尺寸、导出值及误差。用俯视检查轮廓/朝向，用侧视或剖面检查支撑高度、深度、显示体中心偏移；孔槽可用性按 [mechanisms-contact.md](mechanisms-contact.md) 检查。位姿随动通过与空间尺寸通过分别记录。

交付读回沿资产定义 → USD／OS Sites 导出 → 目标消费者核对单位、轴序、全/半尺寸、原点和旋转，确认派生显示与源边界一致。数值与叠加视图均留证；消费者只支持方框时明确近似限制。资产管线负责数据合同、导出映射与读回证据，具体前端绘制实现归消费者维护。未实际运行消费者时写明未验收，不能因数据字段存在就声明显示正确。

## 4. OS graph 与 Blender

1. 建立图节点与模型绑定：设备/资源类、稳定实例 ID、parent/children、局部位置/旋转、配置、资产 ID/修订/摘要、USD 路径及 prim。字段名以实际 OS schema 为准。无法映射的源 occurrence 明确列出，不以猜测注册类填补。
2. 明确资产本体原点、安装锚点、站点锚点及组合顺序。把 CAD 总装位姿去除一次，再由实例变换还原；用非零平移和旋转检查锚点，防止重复应用 CAD 偏移。
3. 单位转换在适配边界显式完成。例如所用 graph 若为 mm、USD 为 m，就在写入/读回时转换；读取实际合同后实施，不将一种项目的单位假设推广给所有 OS graph。
4. 重复对象引用同一固定定义。按可变状态边界组织 USD 实例化；独立移动一个瓶/盖或机构轴后，其他实例保持不变。父级变更时维持预期世界位姿，库位关系通过 OS 结算更新。
5. Blender 作为布局与可视化编辑器：能在 Blender 完成的编辑复用当前适配器；保存后重新读取 OS graph 并重建场景，核对节点数量、关联 ID、局部/世界位姿。`.blend` 是编辑/回看产物，不承担另一份布局或库存权威。
6. IO、交接控制等逻辑设备可以有明确的逻辑绑定，不虚构模型和碰撞体。完整场景中的夹具、机器人、耗材及障碍物都要进入所选规划器实际消费的绑定；渲染存在不等于碰撞场景已接通。

碰撞资产按 [collision-profiles.md](collision-profiles.md) 追加 `simready_usd/collision/` 表示和相应 entrypoints。项目生成器把路径与摘要写入现有 `scene.node_bindings`；OS 复用同一装配计划建立查询场景。资产定义不保存现场当前位姿，抓放后的位姿与携带集合由 OS 当前状态提供。

## 5. 资产脚本与 Python package

拉取、固化、绑定与回归的可执行步骤见 [OS 资产消费与动作绑定](os-asset-binding.md)。先确认实际 OS
工作树同时具备 asset_fetch 与 asset_behavior；README 提及同层模块不证明该分支已经包含实现。

采用现有 `unilab.json.behavior_binding`，避免每个资产再建 pip 项目：

- 数据型资产无需脚本：瓶、盖、架的模型与接口可直接生成资源声明。
- 专属行为放在资产包中，保留 Python Action 签名和元数据。已有设备保留原 owner/action，由领域适配器调用机构行为；独立设备导出可显式生成 `@device` 转发声明。数据资源声明由领域构建器处理，不把行为固化等同自动生成 `@resource`。
- 一个总成可通过 `exports` 导出多个控制对象，例如移液头、针头、泵；不为同一行为重复建立实现。共享行为所有者用已有显式资产引用表达，构建时将所有者一起选中并锁定，不能依赖另一项目的私有模块。
- 源码只依赖包内相对模块、标准库和显式安装的 Python 依赖。领域共用的合同/算法/运行能力用普通 package；现有机器人规划与驱动包继续复用。资产不能隐式导入发布者 checkout、开发路径或工作目录中的脚本。
- 构建时把声明的源码原样固化到工站 `_asset_code/`，入口解析为静态模块；在 assets.lock 记录原包、源文件与派生文件摘要。拒绝源码越界、BOM 漂移、未声明模块和重复注册。不引入动态插件发现、额外行为 DSL 或调度层。
- Python 依赖放 pyproject/安装锁，资产依赖放 assets.lock，实例关系放 graph/bindings。项目工作流保存跨设备顺序；设备过程规则仍由领域作者维护，通用封装器不收录具体工艺。

实际可用元数据通常包括 `kind`、`source_root`、`files`、`implementation` 或 `exports`、`declaration`、`requires`；资产有运动适配器时才声明 `runtime` 等入口。必须先检查现有生成器支持哪些字段；配置文本不能代替执行实现。需要参数化时由声明的实例配置传入，消费方不手改固化源码。

## 6. 原生领域设备包

一个设计项目是一个可安装、可由实际 OS 发现的工作区，沿用其已有结构：

```text
my_station/
├─ pyproject.toml                 # Python 依赖与 package-data
├─ package.yaml                   # OS 包和真实工作流 source / UUID
├─ composition.json               # 若现有生成器使用此项目入口
└─ my_station/
   ├─ __init__.py
   ├─ devices/...                 # 静态设备声明与薄转发
   ├─ resources.py                # 或 resources/；资源与 Sites 声明
   ├─ workflows/...               # 工站工艺 Python
   ├─ layout.json                 # 或 deployment/graphs/ 下既有 OS graph
   ├─ bindings.json
   ├─ assets.lock.json
   ├─ assets/library/...          # 已锁定原生包或现有可解析缓存方案
   └─ _asset_code/...             # 构建生成，消费方不手工维护
```

用最小改动复用现有构建器、领域实现、Catalog 和工作流编译器。共享 runtime 小包是明确维护的能力集合，不是把整个旧仓改名复制。迁移中的旧后端可以显式保留依赖，但必须区分已脱离旧包的路径和仍需旧包的执行路径。

消费方只持有库、蓝图/项目源码和安装依赖。库在服务器；OS/Blender 可以在本地或服务器，不要求多人协同或引入中心调度服务。OS 多项目管理沿用当前实验室中心等已有能力。

## 7. 可复用性验收

按本次范围逐级运行，失败或未接通层保留 `failed` / `not_run`：

1. **定义与封包**：每种可独立操作耗材有定义；原生 schema、摘要、USD 闭包、入口和库索引一致。场景实例数符合装配，几何原型数不随重复摆放线性增长。
2. **图与编辑**：资产去摆放后独立重开，graph 能恢复装配；修改一个实例、保存与重开后，其他实例、源资产及库位局部 frame 不漂移。
3. **OS 包**：实际环境安装/导入、Catalog 设备/Action/资源/Sites、真实工作流 UUID 和语义往返通过。检查 wheel 数据文件；若 OS 工作区需要根目录 manifest，安装交付一并提供并在新目录验证。
4. **动作与结算**：对要求的动作执行真实已接入后端，观察运动/碰撞体并核对库存。覆盖前置拒绝、执行结果不明、目标占用、重复成功回报时的状态；失败时不替换成空实现或假成功。
5. **第二个空项目**：从相同锁定资产组装，改变项目/实例名、布局或数量；不复制修改核心逻辑。验证行为源摘要相同、实例 UUID/可变状态隔离、位姿按新图生效。构建器的原样固化允许，手工 fork 行为不算复用通过。
6. **消费独立性**：移出发布者源码搜索路径，必要时阻断其旧模块导入；从空缓存或授权服务器按固定摘要读取资产，再验证安装/关键动作。只能完成加载时报告加载完成，不能报告工艺运行完成。

动画、理想过程 test doubles、OS 原子结算、真实路径规划/碰撞检查、接触动力学和实机验收各自记录结果。旧工作流编译通过不代表换模组、瓶型、孔数或站点后仍可执行，需要重新检查设备合同和实际流程。

当前 postproc 组合器是完整蓝图的已验证实现，尚不是任意部分资产的通用生成器。迁到其他工站时先查它的固定角色/布局假设，再做必要的最小调整；不要强迫新工站套用 16 类设备或 A 模组。历史项目的成功次数、路径和本机运行环境不是新项目的证据。

## 8. 可选组合粒度与共用资产

同一机构需要“一体式”和“拆分式”两种消费粒度时，一体资产引用可独立使用的子机构定义，设备配方选择其中一种装配；不得把二者同时摆入设备造成重复几何。默认按 [拆分边界](decomposition-boundaries.md) 保留升降模组、完整工具与独立运动采购件；夹持/旋盖一体或分体按明确变体表达。商业成品设备不适用向下拆库资产的规则，除非用户明确指定例外。

跨方案共用采购件先核对型号、几何和运动接口；只凭外观相似不能合并。自制接触件共用须核对顶点、拓扑与局部基准，保留各 occurrence 位姿。同一定义的重复件通过 reference/instance 放置，各实例的活动部件和状态保持独立。装配中间节点明确使用 Xform，验证 Blender 实际导入父子关系及世界位姿。

设备包的几何引用闭包可以携带锁定依赖副本以便离线使用；标准库同时保留可单独消费的子资产，并审计 assembly.dependencies 的固定包摘要。用于绕过查看器长路径限制的 flatten USD 只能作为带来源摘要的派生审阅快照，不能覆盖引用式工程资产。

同时操纵多个物料但沿用单物料结算合同时，明确批次设备占用和逐项结算中间态。故障后运动不明不得写成成功；保存不确定 Claim、设备占用和部分轨迹，不能把诊断游标当作恢复授权或另一套库存。

## 品牌机器人特例

机械臂/末端工具采用 [机器人模块关联](robot-modules.md) 的代码与几何分工。品牌实现作为 Python 依赖安装，资产引用放固定锁，现场装配放 OS graph；通用资产行为封装规则不用于把品牌驱动再复制进资产包。
