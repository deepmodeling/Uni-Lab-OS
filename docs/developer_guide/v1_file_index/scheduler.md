## 说明

- 方法：读每个 V1 文件的文档串和公开类 / 函数，按路由、表名、错误码、字段名、中文术语在统一分支里 grep，有疑问时对照两边测试；
  路由类结论与 `docs/developer_guide/api_v1_route_map.md` 逐条核对过。
- 汇总时改判的两行：`inventory/carrier_snapshot.py`（初判 MISSING → DROPPED #6，入口要求物料是本任务 `task_exclusive` 的 material_source 已准入来源）、
  `inventory/material_io.py`（初判 PARTIAL → DROPPED #6，核验时 material_io 人工补料节点在已定 #6 之列，后来决定补上；其中 load / unload 不只用于补料，见行内备注）。
- 与 已定 #9 或已定设计一致的差异，只写在备注里，不计入 PARTIAL：`/inventory/*` 的读 DTO 用 dev 生命周期词、版本冲突不再回 HTTP 409、命令入参由严格改宽松、
  执行进程重启改为未知执行裁决（R02）、`mark_used` 存为 `retired`。
- 需负责人确认的语义差异（结论见 README「需要确认的三点」），不计数：
  1. V1 里匹配物料只是被其他任务占用（`MaterialClaimedByOtherTask`）时任务等待，不算缺料。统一分支按缺料处理，任务启动即 `plan_not_executable`，就绪时开 `preflight` 决策。V1 只在 material_source 路径做这种区分，所以归 #6。
  2. 容器内容规则放宽，见 content_rules 行。
  3. `material_io` 的 load / unload 是否也属于有意不做，见该行。
- 跨区线索（不在本区计数）：统一分支编译器没有 V1 的 `resource_ref()`、`site_group()`、`material_io()`、`quantity_requirement()`、`with repeat_until(...)` 作者帮助函数，请工作流作者区核实；
  工作流原生库存命令（V1 `workflow/native_commands.py`）整体没有执行器。
