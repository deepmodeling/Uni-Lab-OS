# 工作流跨库库存恢复

调度权威在启动时、动作收尾时，以及运行期间每 5 秒，核对 runtime.db 的 attempt、
冻结派发与开始许可，以及 materials.db 的预留和流水。恢复不调用驱动，不根据扣减推断
物理动作成功。设备参数仍使用 dev 的可读 ID，预留关联使用内部 attempt UUID。

## 结算规则

| 持久执行事实 | 库存处理 |
| --- | --- |
| 当前 pending、已存在 active 预留 | 校验身份、修订和需求摘要后复用，恢复出库参数 |
| succeeded、库存仍 active | 按原预留补扣 |
| succeeded、库存已 consumed | 保持，不再扣减 |
| canceled / failed / timeout / skipped，证明未领用开始许可 | 释放 active 预留 |
| 上述异常终态且领用过许可，或库存已 consumed | 隔离，不把可能使用过的数量加回 |
| 在飞、execution_unknown、intervention_required | 保留库存状态，等待真实回执或现有人工核实流程 |
| 设备仍有样品托管，原本可释放的 active 预留 | 保留到托管释放后再对账 |
| 预留身份、需求或修订不匹配，冻结派发引用缺失记录 | 保留记录，暂停新派发并报告冲突 |

旧作业没有新版开始凭据时，started_at 表示可能执行过，按保守规则处理。
已释放或隔离的库存与成功终态冲突时不会自动返还、重新扣减或解除隔离。
非本工作流权威的预留不参与自动结算；存在本地任务但其 attempt 缺失的记录报错。

## 崩溃窗口与幂等

- runtime 终态提交后、库存结算前退出：下次启动用同一 attempt 继续结算。
- 库存扣减提交后应答丢失：重新读取真实预留状态；不依赖旧进程缓存。
- 若同时查不到库存，保留对账错误，恢复连接后自动重试。
- 已扣库存但执行结果未明确：只保留库存，不写成功，不重复调用设备。
- 任务重建时按 attempt 找回现有预留，只对缺失的未结束 attempt 创建新批次；
  批次幂等键由规范化请求摘要产生，重试、循环和已完成节点不会改变旧请求内容。
- 每项写入前核对调度权威 epoch；旧进程不能在新权威接管后继续结算。

复用现有两库持久事实和 materials.v1 幂等接口，无新增数据库表或 schema 版本。
库存操作只通过 Local / HTTP MaterialsClient，未将两个数据库改为一个跨库事务。
原子性由库存单库事务保证；跨库尚未收敛的阶段通过重复对账完成。

## 观察与重试

`GET /api/v1/scheduler/inventory-recovery` 返回：

- checked_at：最近一次对账时间；
- changed：本次补齐的扣减、释放或隔离（后续轮次没有变化则为空）；
- held：暂时保留的预留及原因；
- issues：失败或冲突，包含可定位的 job_uuid / reservation_uuid。

issues 非空时增加独立暂停原因 inventory_reconciliation；后台重试成功后只清除此原因，
不会取消用户人工暂停或其他暂停来源。历史账务变更仍查 materials 库流水，诊断快照只代表最近一轮。
恢复与重试本身不要求重启 Host 或 slave，部署新代码仍遵守先提示、手动确认重启的约定。

## 验证范围

新增真实双 SQLite 库测试覆盖关闭重开、提交后应答丢失、跨连接并发、旧权威 fencing、
身份漂移、未知执行、托管阻止释放、后台空闲重试、诊断 API 和真实 HostLink 虚拟驱动调用。
HostLink 测试验证调用驱动前已消费预留、调用一次、重开两库后数量不再扣减。
这不代表真实实验硬件、多 slave 或部分实际用量结算已经完成验收。
